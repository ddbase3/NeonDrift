# Neon Drift: technical privacy and data-handling inventory

**Source review:** 2026-10-14, NeonDrift 0.3.0. Source evidence: `src/Display`, `src/Output`, `src/Service`, `src/NeonDriftPlugin.php`, `tpl/Display`, `assets/js`, `assets/css`, language files, and `base3.json`. This is an inventory of the module's code, not a legal privacy notice or a claim that an operator's deployment complies with GDPR.

## 1. Scope and controller responsibility

Neon Drift is a BASE3 browser game, optionally storing a personal checkpoint and best score after explicit user activation. The BASE3 installation or embedding host serves assets and pages, supplies authentication, session management and a configured `ISettingsStore` implementation, and decides who may access the Games administration tab. The operator must identify its own controller/processor, legal basis, lawful information duties, retention schedule, and any applicable GDPR (EU 2016/679), ePrivacy (2002/58/EC), EAA (EU 2019/882), WAD (EU 2016/2102), national laws and EN 301 549 requirements. None can be inferred from plugin code alone.

## 2. Processing without saving

The game simulates ship movement, random obstacles, warnings, level progress, keyboard/pointer/touch input, energy, combo, score, hits, elapsed time, and visual effects locally in the user's browser. Native fullscreen changes browser presentation only. Optional sound effects are synthesized in browser memory with Web Audio after a deliberate click, with sound disabled by default. Neither the fullscreen state nor the audio preference is persisted or sent to any network service. It transmits no telemetry, keyboard sequences, movement trajectories, game analytics or external network beacons. Scores remain in the active browser widget unless the player saves them. Restart replaces the current run; removal of the AJAX game tab removes browser-side listeners and the simulation loop. The HTML and assets use the host's normal request and caching paths.

The module creates no browser localStorage, sessionStorage, IndexedDB entries or browser cookies. However, the BASE3 host's existing session may rely on cookies, and HTTP requests and session mechanisms can create host logs or metadata. The game's `GET` profile request occurs on mount, only against a same-origin BASE3 endpoint, to determine whether the optional profile capability is available. That request uses the host session if one is active.

## 3. Optional saved player profile

Once the user explicitly chooses **Save Checkpoint**, the game sends JSON to `NeonDriftProfileOutput` using the first-party URL generated by `ILinkTargetService`. The endpoint uses `IUsermanager` and `ISession` to verify an authenticated, active session and binds all reads/writes to the current user ID. The server-side record name is `user_` followed by SHA-256 over the BASE3 user ID, within the `ISettingsStore` group `neondrift_player_profiles`. This derived identifier is **pseudonymous**, not anonymous, and remains linkable to the same account across sessions. The client cannot supply the key or another user's ID.

Stored fields are limited to `version`, best score (`best`), best reached level (`best_level`), a single `checkpoint` with level, score, remaining energy, elapsed seconds and UTC save timestamp (`saved_at`), and UTC update timestamp (`updated_at`). Numbers have server-side input bounds and a JSON-only interface. No name, e-mail, text messages, ILIAS course information, device identifier or raw game controls are included in the settings record. Stored gameplay scores are client-reported and are **not anti-cheat verified**.

A successful explicit save opts the player into subsequent automatic checkpoint updates at level completion and best score recording after game over. Automatic updates cannot replace a checkpoint with a lower-level one; explicit saves can. Reading the profile includes a session-bound CSRF token, generated with a cryptographic random source and stored under `neondrift.profile.csrf` in the host session. Mutating requests require that token, JSON POST and a valid authenticated session. Token retention follows the host session lifecycle. All JSON responses are marked `Cache-Control: no-store`; the host can impose additional security and caching rules.

## 4. Storage backend and retention

NeonDrift adds **no** SQL tables, migrations, filesystem store, job, queue, audit log or external processing service. `ISettingsStore` owns the backend and can be bound by the host to a database, file-based implementation or non-persistent implementation. Profiles only persist if the configured backend actually supports it. The plugin does not set an automatic expiration or retention limit: profiles remain until deleted by the player, removed by the host or expired according to the operator's backend policy. The session CSRF token remains only for the current host session according to that host's policy.

**Known retention gap:** no operator retention schedule, database maintenance, encryption-at-rest, session expiration settings or backup lifecycle were provided. Deployments that persist profile data must define appropriate retention/deletion, disclosure and backup handling procedures. Do not infer any automatic deletion guarantee for historic backups.

## 5. Access, security and erasure

Each profile request is scoped server-side to the authenticated `IUsermanager` user identity; anonymous requests or requests without an active session receive an error. POST actions require valid CSRF token and application/json content type. Only `save`, `advance`, `record` and `delete` operations are accepted. The game does not use client-supplied record keys or offer a list of other profiles. Best scores are personal rather than publicly ranked. The operator must still review the active framework route, host permissions, session implementation, logging and CSRF behavior in its deployment.

The **Delete Data** button calls the authenticated endpoint to remove the player's single settings dataset, including best score and checkpoint. The frontend blocks any newly initiated automatic saves while deletion is in progress, and checks the deletion response. The storage service checks that the record was actually removed. New records are not created after successful deletion unless the player explicitly saves again. Saved data is read back into the game only on user instruction via **Load Save**. Data rectification can be achieved by a new explicit save, and the host must handle any additional statutory requests including access/export and backend backup erasure where required. No automatic export endpoint is implemented here.

## 6. Recipients, transfers and external services

The feature sends no gameplay data to a third-party endpoint. The authenticated profile endpoint and static assets are resolved by the host BASE3 implementation. Access by host infrastructure, system administrators, settings-store operators, processors, log providers, content distribution layers or backups depends on the installation and has not been examined. Country, cross-border transfer, data recipient, subprocessor and organizational security claims are unknown and must be established by the operator.

## 7. Logging, security, backups and known gaps

The plugin deliberately does not write score events to an application logger. HTTP access logs and errors, PHP/runtime logs, monitoring, authentication/session logs and backup copies may nevertheless be created by existing host infrastructure. Their content, retention and deletion paths are not verifiable from this code. JavaScript assets may be cached according to normal browser and server policies; game profile JSON responses expressly request no-store behavior.

This plugin does not require its own credentials or database permissions. It relies on the security of the configured `ISettingsStore`, session system, usermanager and host routing. There is no independent leaderboard fraud detection. The optional profile endpoint does not introduce a new cross-site network dependency.

## 8. Accessibility and deployment validation

Neon Drift provides native keyboard-operable buttons, keyboard and pointer/touch steering, textual progress and a semantic progressbar, an ARIA live status, keyboard focus management, high-contrast control styles, audio opt-in and a dynamic reduced-motion setting for decorative effects. However, hazards are spatially represented in Canvas, and equivalent non-visual gameplay is not yet provided. Full WCAG 2.2 AA or EN 301 549 conformance cannot be claimed. Operators must test focus/keyboard, responsive zoom, contrast, announcements with screen readers, touch input, reduced motion and their host admin/AJAX integration.

Before production deployment, verify: active user and session semantics, ISettingsStore durability and user separation, route behavior and authorization, HTTPS and CSRF, DB/file retention, backup removal, host logging/caching, browser/CSP behavior, applicable privacy notices, and the accessibility limitations above. No invented compliance certifications, hosting assurances, or global retention values are implied by this source inventory.
